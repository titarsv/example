# План: ИИ-импорт свёрстанных страниц (лендингов) в CMS

Дата фиксации: 2026-08-12 (скоуп сужен в тот же день — см. правку ниже)

## Контекст и цель

Верстальщики регулярно сдают готовые статические лендинги (пример — `C:\Development\Layouts\vza`:
webpack-сборка `dist/` из HTML-страниц `index/about/contacts/impressum/datenschutz/404`). Сейчас
каждую такую страницу на CMS «сажают» руками: создают шаблон, копипастят вёрстку, заводят поля,
грузят картинки, переносят тексты. Перенос CSS/JS в тему (scss-файлы, `app.js`) верстальщик/
разработчик по-прежнему делает вручную копированием в папку темы — **этого импорт не касается**.
Автоматизируем только контентную часть: залил ZIP архива `dist/` → ИИ находит и выделяет основной
контент страницы (без хедера/футера/меню — это уже даёт тема) → на выходе шаблон страницы
(Blade + схема полей, как в разделе «Шаблоны страниц»), залитые в медиатеку картинки контента
и заполненная данными страница.

Решения по архитектуре (зафиксированы с пользователем):

- **Импорт не трогает CSS/JS.** Ни скоупинга, ни переноса стилей/скриптов — это ручной процесс
  разработчика (копирует `.scss` и `.js` файлы донора в папку темы отдельно от импорта). Задача
  импорта — только контент: разметка `<main>`, тексты, картинки.
- **Импортированные страницы встраиваются в тему магазина** — используют общий `header`/`footer`/
  корзину/меню из `public.layouts.main`. Из исходного HTML в шаблон идёт только контент `<main>`
  донора (хедер/мобильное меню/футер донора выбрасываются — дублируют то, что даёт тема).
- **Максимальная гранулярность полей** — каждый смысловой текстовый узел (заголовок, абзац,
  подпись), каждая картинка контента и каждая инлайн-иконка `<svg>` становится отдельным полем
  схемы (в духе уже реализованной ACF-подсистемы: `text`/`wysiwyg`/`oembed`/`gallery`/`repeater`/
  `group`, см. [[acf-improvements-plan]]). Только разметка-«скелет» (сетка секций, обёртки,
  классы) остаётся зашита в Blade как есть, полем не становится.
- **SVG-иконки — тоже контент, не декорация.** Инлайновый `<svg>…</svg>`, встречающийся внутри
  `<main>` (в vza — вообще все иконки инлайновые), при импорте (а) сохраняется как отдельный
  `.svg`-файл и заливается в медиатеку через тот же `File::createFile()`, что и обычные картинки,
  и (б) сама разметка SVG кладётся значением в текстовое поле схемы (не как отдельный «image»-тип
  со ссылкой на файл, а как raw-markup в `text`/`wysiwyg`-поле, отрисовывается через `{!! @field(...) !!}`
  — так уже устроен рендер HTML-полей в теме, см. `resources/themes/base/.../pages/about.blade.php`).
  Заливка в медиатеку даёт переиспользуемый файл в «Медиа», значение в поле — редактируемость
  прямо в схеме страницы.
- **Вход — ZIP с готовой `dist/`-сборкой**, как в примере vza: HTML уже собран, картинки уже
  захэшированы в имени файла.

## Что уже есть в проекте и на что опираемся

- `Modules/Ai` — `AiServiceInterface` + `GeminiService`/`OllamaService`. Активный провайдер сейчас
  `AI_PROVIDER=ollama` (локальная `llama3.1:8b`, `OLLAMA_URL=http://localhost:11434`), но интерфейс
  провайдер-агностичный — переключение на Gemini (ключ уже в `.env`) не требует правок кода импорта.
  Паттерн вызова везде одинаковый: промпт с жёстким требованием «верни только JSON» → `json_decode`
  (у Ollama есть нативный `format: 'json'`, у Gemini — обрезка ```json оградки).
- Система шаблонов страниц (родственный план — [[acf-improvements-plan]]): схема полей в `settings`
  (`template_public.layouts.pages.{name}`) + `.fields.json` рядом (Local JSON sync), сам Blade —
  через `Storage::disk('local')`. `HasCustomFields`, `Fields::value()`/`@field()`,
  `Fields::validateSubmission()` — весь автобиндинг уже готов, импорту достаточно генерировать
  Blade с `@field('slug')` и класть значения в `fields` в том же формате, что и ручное сохранение.
  Готовые типы полей: text, textarea, wysiwyg, oembed, gallery, select, product, relationship,
  taxonomy, repeater, group, number, email, url, date, color, true_false.
- Медиатека — `App\Models\File::createFile(['title','path','type','hash'])`, дедуп по `md5_file`,
  файлы физически в `public/uploads` (см. `MediaController::adminUploadAction`).
- Создание страницы — `Page::insertGetId(['template' => ..., 'status' => 0, ...])` →
  `$page->saveSeo($rd)` (url/meta) → `$page->saveLocalization($rd)` → `Action::createEntity($page)`.
- ZipArchive расширение PHP доступно — распаковка без внешних зависимостей.

## Риски, которые план обязан закрывать

1. **Маленькая локальная модель.** `llama3.1:8b` по умолчанию — не гарантирует надёжный разбор
   сложной вёрстки за один проход, особенно с ограниченным контекстным окном Ollama. **Решение**:
   до отправки в ИИ заменяем громоздкий `<svg>…</svg>` (в примере vza — добрая половина байт
   about.html, в основном `path d="…"` координаты) и `style`-атрибуты на короткие плейсхолдеры
   (`__ICON_1__`) — ИИ работает с обозначением узла и его позицией в дереве, не с самой геометрией
   SVG. После ответа модели плейсхолдер разворачивается обратно в реальный SVG-markup при сборке
   значения поля (см. 0.4/1.3) — модель просто должна пометить узел как поле нужного типа, не
   пересказывать координаты путей. Промпт собираем на ОДНУ html-страницу за раз, не на весь архив.
   Провайдер переключаемый — если качество разбора хромает, эксплуатация может временно перейти на
   Gemini через `.env` без правок кода.
2. **ИИ ошибается — нужен предпросмотр перед публикацией.** Импорт не должен сразу создавать
   боевую страницу. Черновой шаблон + черновая страница (`status = 0`, как у обычных страниц)
   создаются сразу, но с обязательным шагом ревью в админке (вкладки «Поля»/«Шаблон»/«Превью» —
   уже есть в редакторе шаблонов, см. [[acf-improvements-plan]] этап 2.2) перед включением показа.
   Превью в этом режиме будет без стилей донора (они ещё не перенесены разработчиком в тему) —
   это ожидаемо, ревьюер проверяет структуру полей и данные, не финальный вид.
3. **Разметка донора ссылается на классы, которых в теме ещё нет** (CSS переносится отдельно,
   вручную, возможно даже позже импорта). Шаблон генерируется с исходными классами донора as-is —
   это осознанно: как только разработчик скопирует `.scss`/`.js` в тему, страница «доедет» без
   правок Blade. Задача импорта — не подгонять разметку под тему, а сохранить её как есть.

## Порядок реализации

0 → 1 → 2. Стартуем с 0.1–0.4 (загрузка/распаковка/выделение `<main>`/перенос картинок) — это
чистая механика без ИИ и без риска, дальше контрольный ручной прогон 0.5 на примере vza/about,

## Заметки по ходу реализации этапа 2

- **2.1/2.2**: `Modules/PageImport/app/Services/PageBuilder.php` — оркестратор ОДНОЙ страницы:
  парсинг → перенос ассетов → препроцессинг → `analyzePageMarkup()` → `SchemaBuilder::build()` →
  запись blade+settings шаблона (тот же механизм, что «Дублировать» в разделе «Шаблоны страниц») →
  `Page::insertGetId()` → `saveSeo()`/`saveLocalization()` (черновик, `status=0`). Служебные
  страницы донора (`404`/`403`/`500`/`error` — по имени папки/файла) пропускаются со статусом
  `skipped`, не долетая до ИИ и записи файлов. Название страницы — из `<title>` донора (вне
  `<main>`, поэтому читается напрямую из raw html, не через `ArchiveParser`); slug шаблона — из
  имени папки файла (`about/index.html` → `about`, корневой `index.html` → `home`, как у уже
  существующих шаблонов темы).
  **Коллизия имён — реальный риск, а не гипотетический**: сайт из примера уже имеет шаблоны
  `about`/`contacts`/`home` — при столкновении `PageBuilder::uniqueTemplateName()` подбирает
  `{name}-import-N`, не перезаписывая существующий файл. Проверено вживую — донор снова назвал
  свою страницу "about", получили `about-import-2`, оригинальный `about.blade.php` не тронут.
  Мультиязычность — по решению 1.5: основная локаль (`config('app.main_locale')`, у этого сайта
  это `ru`, не `ua`!) получает реальные значения донора, остальные — ту же схему с пустыми
  value/data (черновик под перевод).
- **2.3**: `Modules/PageImport/app/Jobs/ProcessPageImportJob.php` (`ShouldQueue`, `$tries=1` —
  повтор задвоил бы уже созданные шаблоны/страницы) перебирает `pages[]` (уже провалидированные
  на 0.3/0.4), для каждой вызывает `PageBuilder::build()`, сохраняет прогресс в новую колонку
  `imported_pages` **после каждой страницы** (не одним махом в конце) — если импорт из многих
  страниц упадёт на середине, уже собранные не потеряются. Статус импорта: `PROCESSING` на
  старте → `REVIEW` (нашлась хотя бы одна собранная страница) или `ERROR` (ни одной) в конце.
  Диспатчится из `adminUploadAction` сразу после валидации 0.3/0.4.
- **2.4**: экран `/admin/page_imports/review/{id}` — таблица результатов по каждому файлу архива
  (создано/пропущено/ошибка + причина), ссылки на редактор страницы и шаблона, кнопка
  «Опубликовать» на черновик (`adminPublishPageAction`, POST) — когда все страницы импорта
  опубликованы, весь импорт помечается `PUBLISHED`. Пункт «Ревью» появляется действием в общем
  списке импортов только при статусе `REVIEW`/`PUBLISHED`.

**Живой прогон целиком (реальная очередь Redis, не в обход)**: загрузил архив через форму →
джоба ушла в очередь → поднял `queue:work --once` фоном → через ~3.5 минуты (5 живых вызовов
Gemini подряд) получили `status=REVIEW`, `log: "Собрано страниц: 4, ошибок: 1"`. Из 6 файлов
архива: `404` пропущен, `about`/`contacts`/`impressum`/`index`(→`home`) собраны и создали
реальные Page с реальным контентом, `datenschutz` (самая длинная страница, ~15KB) упал с
`ai_analysis_failed` — сетевой idle-timeout на стороне Gemini API для особо большого контента,
джоба корректно залогировала ошибку по ЭТОЙ странице и продолжила остальные, не уронив весь батч.
Экран ревью открыт, кнопка «Опубликовать» отработала (страница получила `status=1`, бейдж сменился
на «Опубликовано»).

**Два серьёзных бага пойманы ИМЕННО на этом живом прогоне** (не всплывали раньше, потому что
раньше не доходило до реального сохранения Page/Localization — тестировались только сервисы
в изоляции):

1. **`Class "Fields" not found` при первом же открытии реально созданной страницы на сайте.**
   Директива `@field()` (заведена ещё на этапе ACF-плана, [[acf-improvements-plan]]) компилировалась
   в неквалифицированный `Fields::value(...)` — скомпилированный blade-файл выполняется без
   `namespace`/`use`, поэтому `Fields` резолвился в global-неймспейс, где такого класса нет.
   Раньше это не ловилось, потому что вся проверка блейда шла через `blade_check.php`
   (`php -l` на скомпилированный вывод) — она видит только СИНТАКСИЧЕСКУЮ валидность PHP,
   `Fields::value(...)` синтаксически корректен независимо от того, резолвится ли класс. Поймали
   только на реальном рендере страницы в браузере. **Исправлено в `app/Providers/AppServiceProvider.php`**
   — директива теперь эмитит `\App\Helpers\Fields::value(...)` (полное имя). Это касается ВСЕХ
   мест, где используется `@field()`, не только импорта страниц.
2. **Данные новой страницы (имя, текст полей) выглядели пустыми в её собственном редакторе,
   хотя в БД лежали верные значения.** Причина — `Relation::morphMap()` регистрируется в
   `AppServiceProvider::boot()` только вне консоли (`if(app()->runningInConsole()) return;`), а
   **очередь ("queue:work") — это тоже консольный контекст**. Без morph-карты `Page`/`Seo` при
   создании `Localization`/`Seo` записей из джобы сохранялись с ПОЛНЫМ именем класса
   (`App\Models\Page`) вместо алиаса (`Pages`), которым реальный веб-запрос (где карта
   зарегистрирована) ищет эти записи — находил 0 строк, хотя они существовали под другим
   `*_type`. **Исправлено локально** — в `PageBuilder::createPage()` перед `saveSeo()`/
   `saveLocalization()` явно регистрируем нужную часть карты (`Pages`, `Seo`), не трогая общий
   `AppServiceProvider` (это затронуло бы вообще все консольные команды/джобы проекта — более
   широкое, не обязанное этой задаче изменение). **Это системный риск для ЛЮБОЙ новой очереди
   в проекте, которая создаёт (не только обновляет) полиморфные записи** — стоит иметь в виду,
   если в будущем появятся другие джобы, пишущие Localization/Seo/etc с нуля.

**Ограничение окружения (не баг):** список импортов не сразу показал новую иконку «Ревью» после
правки `page_imports.js` — тот же давно известный по прошлым сессиям агрессивный кэш статик-JS
в этом браузере, который не сбрасывается даже принудительным reload. Функциональность подтверждена
напрямую (прямой переход на `/review/{id}` и AJAX-проверка ответа сервера), это не имеет отношения
к реальным пользователям/чистым браузерным профилям.

Тестовые страницы/шаблоны/медиафайлы/PageImport-запись после каждого прогона полностью удалены,
count(Page) вернулся к исходным 7.

     курсором: поиск ведём от позиции конца предыдущей найденной замены, откатываясь к поиску
     от начала документа только если с курсора не нашлось (курсор сбрасывается после каждого
     repeater — его схлопывание меняет разметку слишком сильно, чтобы отсчёт позиций
     оставался надёжным).
  2. Простой резолвер CSS-подобных селекторов для детей repeater'а трактовал совпадение
     селектора с тегом самого инстанса (`"div"` при `<div class="trading-item">`) как «это сам
     инстанс» — из-за чего `textContent`/`innerHTML` захватывал ВЕСЬ инстанс целиком, включая
     соседний узел с иконкой (плейсхолдер `__ICON_N__` внутри текста потом разворачивался в
     реальный SVG прямо внутри текстового поля). Убрал этот случай — совпадение с тегом больше
     не считается «резолвится в себя», только явно пустой селектор.
  3. Даже после фикса (2) модель иногда сама даёт для текстового поля repeater-элемента
     недостаточно узкий селектор, из-за чего в значение всё равно может попасть иконка соседа —
     добавлена защитная зачистка `__ICON_N__` из value ПЕРЕД восстановлением плейсхолдеров, но
     **только для детей repeater'а** (там почти всегда есть отдельное родственное поле типа
     "icon", забирающее иконку на себя явно — потеря контента маловероятна). На верхнем уровне
     эту зачистку сознательно НЕ делаем — там нет гарантии соседнего icon-поля, и вырезать
     иконку означало бы молча терять кусок разметки донора, а не просто пачкать одно текстовое
     поле лишним markup'ом.
  **Ограничение было — исправлено позже, см. «Доработка границ repeater'а» ниже.**
  **Проверено на обеих тестовых страницах** (несколько прогонов, Gemini): схема генерируется
  корректно (id/type/name/slug/fields), Blade компилируется без ошибок (через тот же
  `blade_check.php`, что и в прошлой сессии), утечек markup в нетиповые поля на финальных
  прогонах не найдено (grep по `<svg` во всех НЕ-icon-полях — 0 совпадений).

## Доработка границ repeater'а (после этапа 2)

Закрыл ограничение из 1.3: `SchemaBuilder::expandToRepeatBoundary()` поднимается по DOM от
найденных по классу узлов вверх, пока это ОДНОЗНАЧНО тот же повтор — узлы-кандидаты ещё не прямые
сиблинги друг друга (иначе граница уже верная, поднимать некуда), а их родители сиблинги ОДНОГО
тега под общим "дедом". Совпало — берём родителей как границу репитера; не совпало — останавливаемся
на исходном уровне, ничего не портим (осознанно консервативно: ложный подъём хуже, чем отказ от
подъёма). Максимум 3 уровня вверх, дальше не пытаемся — не должно понадобиться, а любой лишний
уровень увеличивает риск случайно поймать что-то совсем постороннее.

**Оказалось, что это не единичный баг, а системная особенность донора**: у vza ВСЕ карточные
repeater'ы (`.trading-item`, `.tips-item`, `.advantages-item`) завёрнуты в сетку-колонку
(`.col-lg-3.col-md-6` / `.col-lg-6.col-md-12` / `.col.col-txt`) — обычный Bootstrap-паттерн для
любой карточной раскладки. Значит на живом прогоне этапа 2 (4 успешно созданные страницы) этот
баг, скорее всего, проявлялся везде, где был repeater, просто не был отдельно проверен на
конкретных полях кроме `trading_advantages`.

**Проверено** (синтетический ответ ИИ — без реального вызова, чтобы не ждать/не тратить квоту —
но с реальным контентом `index.html` через уже протестированные `ArchiveParser`/`AssetImporter`):
все три repeater'а донора (`trading_advantages`, `tips_list`, `key_advantages`) корректно
схлопнулись вместе с сеткой-обёрткой, 0 пустых `<div>`-обёрток на выходе (было — 3 пустых только
у `trading_advantages`), по одному `@foreach`-блоку на каждый, значения по строкам разные (не
задваивают пример). Итоговый Blade компилируется (`blade_check.php`). Тестовые медиафайлы,
созданные по ходу (`AssetImporter` реально дергался на каждый прогон), удалены.

## Ретраи ИИ-таймаутов на больших страницах

Закрыл `datenschutz.html`-кейс из живого прогона этапа 2 (Gemini уронил самую длинную страницу
донора, ~15KB контента, по "Idle timeout reached"). Две независимые правки:

1. **Причина таймаута** — `GeminiService` строил клиент через `Gemini::client($key)`, который
   находит HTTP-транспорт через PSR-18 discovery; в этом проекте это оказался Symfony HttpClient
   с дефолтным idle-таймаутом, ощутимо более коротким, чем нужно модели на генерацию по-настоящему
   длинного ответа. Теперь `GeminiService` сам собирает клиент через `Gemini::factory()
   ->withHttpClient(...)` с явным `Symfony\Component\HttpClient\Psr18Client` (`timeout: 120,
   max_duration: 180`) — щедрее дефолта. Это меняет клиент для ВСЕХ методов `GeminiService`, не
   только `analyzePageMarkup()` — дольше таймаут не создаёт новых сбоев на быстрых запросах,
   только помогает медленным.
2. **Ретраи** — `BuildsPageMarkupPrompt::withRetries()` (общий trait, значит один раз на оба
   провайдера): до 3 попыток с 5-секундной паузой между ними, ловит и сетевые исключения
   (таймаут/обрыв), и `null` от `parsePageMarkupResponse()` (невалидный JSON и т.п.). Вызывается
   `sleep()` — это осознанно нормально, `analyzePageMarkup()` дёргается ТОЛЬКО из очереди
   (`ProcessPageImportJob`), синхронный sleep между попытками не блокирует ничей HTTP-запрос.

**Проверено на реальном упавшем кейсе**: прогнал `datenschutz.html` через `PageBuilder` заново —
раньше падал с `ai_analysis_failed`, теперь `status: "created"` за 85.4с (успех с одной из
первых попыток, не потребовалось всех 3 — щедрее таймаут сам по себе уже решил проблему для этой
конкретной страницы, ретраи — подстраховка на будущее для действительно нестабильной сети/API).
Тестовая страница/шаблон/медиафайлы удалены после проверки.

### Находка 1 — реальный баг: «осиротевшие» поля-дети repeater'а

**Подтверждено с полной трассировкой (не гипотеза).** У двух из шести страниц (`cryptocurrency`,
`faq`) схема repeater'а содержит БОЛЬШЕ дочерних полей, чем реально расставлено в Blade:

- `crypto_steps`: схема объявляет `step_number` / `step_title` / `step_body_content` — в Blade
  реально подставлен `@field`-эквивалент только для `step_body_content`; `step_number`/`step_title`
  остаются пустыми редактируемыми полями в админке, но правка любого из них **не меняет
  отрендеренную страницу** — там жёстко зашит текст первого инстанса ("1", "Fetch and Install
  Trustee Plus").
- `faq_items`: схема объявляет `question` / `icon_1` / `icon_2` / `answer` — расставлены только
  `icon_1`/`icon_2`; `question`/`answer` жёстко зашиты (текст и ответ первого вопроса), поле в
  админке есть, эффекта от его правки — нет.

**Причина найдена в `SchemaBuilder::processRepeater()`** (~строки 190–198): для нерепитерных типов
поля (`text`/`wysiwyg`/…) `$childSchema[] = $this->schemaEntry(...)` вызывается **безусловно**,
даже если непосредственно перед этим попытка вставки `@field($item, 'slug')` в тело `@foreach`
провалилась (`$childValue === ''` — `resolveChildValue()`/`resolveSimpleSelector()` не смогли
однозначно найти под-узел по селектору от ИИ, ЛИБО `str_contains($loopBody, $childValue)` не
нашёл текст дословно). Ветки `icon`/`image` расставляют `@field` условно (`if(preg_match(...))`,
`if($imgNodes->length > 0)`), но это условие не влияет на `schemaEntry()` дальше по коду — она
всё равно выполняется. Итог: поле «протекает» в схему/админку, даже когда физически никуда не
вписано — тихая, необнаруживаемая на глаз ловушка для редактора контента (правишь поле, ничего не
меняется, узнаёшь только сравнив рендер с ожиданием).

Не проявилось в этой форме на vza, потому что там `resolveSimpleSelector()` успешно резолвил
селекторы ИИ для всех детей repeater'ов на обеих тестовых страницах — donor-специфично, зависит от
того, насколько ИИ (Gemini) даёт разрешимый `selector_path` для конкретной разметки.

**Исправлено** (по решению пользователя, сразу после находки): `SchemaBuilder::processRepeater()`
теперь пушит `schemaEntry()` в `$childSchema` только если сплайс `@field`/`field($item, ...)` в тело
`@foreach` РЕАЛЬНО произошёл — заведён явный флаг `$spliced`, выставляется `true` в каждой из трёх
веток (`icon`/`image`/остальные) ровно там, где раньше объединение с телом цикла молча могло
провалиться, `schemaEntry()` теперь под `if($spliced)`. `$rows[*][$childSlug]` (значения по строкам)
трогать не стал — лишний ключ в массиве значений безвреден, `fillSchema()` на этапе создания
страницы обращается только к слагам из `$childSchema`, несуществующий (для админки) слаг в `$values`
просто никогда не читается.

**Проверено юнит-тестом на синтетическом ответе ИИ** (без живого вызова — детерминированно и без
расхода квоты), с реальным содержимым `cryptocurrency.html`:
- Негативный кейс (воспроизводит реальный баг): составные селекторы `.crypto-item__head span` /
  `.crypto-item__head div` для `step_number`/`step_title` (`resolveSimpleSelector()` поддерживает
  только `tag`/`tag.class`/`:nth-of-type(N)`, составные — не резолвит) → оба поля теперь корректно
  ОТСУТСТВУЮТ в `$childSchema` и в `field($item, ...)`-ссылках Blade; `step_body_content` (простой
  однозначный `.crypto-item__body`) — на месте, как и раньше.
- Позитивный кейс (регрессия): тот же repeater, но `step_number` с РАЗРЕШИМЫМ простым селектором
  (`span`) — поле корректно остаётся в схеме, и по строкам получает РАЗНЫЕ значения ("1", "2", …),
  не задваивая пример первого инстанса — старое поведение не сломано.

`php -l` на изменённый `SchemaBuilder.php` — без ошибок. Тестовые медиафайлы, созданные побочно
при обоих юнит-тестах (реальные вызовы `AssetImporter::importImages()` на `cryptocurrency.html`),
удалены, `File::count()` вернулся к 2735.

### Находка 2 — ограничение ИИ-разбора: пропущенные repeater'ы целиком (исправлено)

`about` (6 одинаковых по структуре "mission"-карточек: иконка + заголовок + текст) и `telegram`
(повторяющиеся блоки в SEO-тексте) — ИИ (Gemini) в первом прогоне **вообще не завёл под них ни
отдельных полей, ни repeater** — весь этот контент был зашит в Blade как статичный текст донора,
включая картинки. Хуже находки 1: там поле хотя бы ЕСТЬ, просто не работает; здесь поля не было
вовсе. Разобрался в двух независимых причинах и исправил обе:

1. **Код в принципе не умел искать repeater без класса на самом повторяющемся элементе.**
   `about`'s карточки — голые `<div>` без единого класса, общий класс есть только у ОБЁРТКИ
   (`.about-main__wrapper`), не у повторяющихся детей. Прежний `processRepeater()`
   (`lastClassToken()`) брал последний токен селектора и искал `.class` в нём — при "голом" теге
   без класса это гарантированно `null`, репитер отбрасывался ДАЖЕ если бы ИИ его правильно
   разметил. **Исправлено**: новый `SchemaBuilder::findRepeaterInstanceNodes()` поддерживает второй
   случай — если последний токен селектора не содержит класс, но это простой тег (`div`), а более
   ранний токен содержит класс контейнера (`.about-main__wrapper > div` /
   `.about-main__wrapper div`) — ищем контейнер по классу и берём его ПРЯМЫХ детей с этим тегом.
   Прежнее поведение (класс на самом инстансе, `.trading-wrapper .trading-item` и т.п.) не
   изменилось, просто вынесено в тот же метод.
2. **Промпт не объяснял ИИ, что повтор может быть без общей обёртки-класса на элемент, и не
   запрещал непригодные для резолвера составные селекторы у детей.** Добавлены в
   `BuildsPageMarkupPrompt`: Пример 2 (repeater без класса на инстансе, ровно паттерн `about`),
   правило 8 ("любая однородная последовательность из ≥3 блоков — repeater, даже без общего
   класса и даже если это не 'карточки' на вид"), правило 9 (селекторы детей — ТОЛЬКО простой тег/
   тег.класс/`:nth-of-type(N)`, явный запрет составных — снижает и частоту находки 1), правило 10
   (не оставлять крупный контент вообще без поля — заводить hopIC хотя бы "wysiwyg").

**Побочный фикс той же природы, найденный по ходу**: repeater, у которого ни один дочерний узел не
сплайсился (или ИИ вовсе не дал `children`) — раньше всё равно попадал в схему с ПУСТЫМ списком
полей (`faq_categories` в живом прогоне — 5 строк, 0 полей: бесполезная карточка в админке без
единого поля для заполнения, и риск размножить статичный текст первого инстанса на N копий при
рендере). Добавлен тот же принцип, что и в находке 1: пустой `$childSchema` после обработки детей →
репитер целиком отбрасывается, содержимое остаётся как в исходной разметке donor'а (не хуже, чем до
репитера).

**Проверено дважды.** Юнит-тестом на синтетическом ответе ИИ (реальный `about.html`, вручную
воспроизведён селектор `.about-main__wrapper > div` — ровно то, что теперь просит промпт) — все 6
карточек корректно схлопнулись в repeater с 3 полями (`icon_image`/`title`/`text`), у каждой строки
СВОИ значения, Blade компилируется. И — что важнее — **живым прогоном с реальным вызовом Gemini**
(см. «Финальная сквозная проверка» ниже): модель САМА, без ручной подсказки, увидела и разметила
и `about`-карточки (`about_features`, 3 поля, 6 строк), и `telegram`-блоки (`telegram_feature_blocks`,
2 поля, 2 строки), и вдобавок разложила весь ранее полностью статичный SEO-текст `telegram` на 7 пар
`{заголовок, wysiwyg-контент}` полей — то есть решила даже кейс "плоское чередование `<h2>+<p>` без
общей обёртки", который заведомо не покрывает пункт (1) выше (там нет DOM-репитера, это не связанные

### Находка 3 — неразличимые имена страниц (исправлено)

Все 6 страниц донора получили одинаковое имя **"ProperLoud"** — `PageBuilder::extractTitle()`
корректно читает `<title>`, но у этого донора `<title>` — статичный бренд-плейсхолдер, одинаковый
на каждой странице собранного `dist/` (реальный заголовок, судя по всему, проставляется на клиенте
JS-ом после гидратации SPA, в статике его нет).

*Поправка к первой версии этой находки*: формулировка "у vza `<title>` был уникальным на каждой
странице" была ошибочной, проверено дополнительно постфактум — у vza `<title>` тоже одинаковый на
всех страницах (`Versilbertes und Zinn Ankauf`, реальное название бизнеса донора). Значит это не
специфика конкретно proper-loud, а типичный паттерн для готовых webpack-сборок — тем полезнее
оказался фикс.

**Исправлено**: `ProcessPageImportJob::extractDuplicateTitles()` — лёгкий предварительный проход по
ВСЕМ страницам батча ДО тяжёлого разбора (только чтение `<title>` через тот же

на этих страницах игнорируется в пользу `titleFromPath()` — ровно то же поведение, что и при
полностью пустом `<title>`. Заголовок, уникальный в батче, работает как раньше без изменений.

**Проверено** на реальных файлах обоих доноров (без живого вызова ИИ, чтение `<title>` — чистая

## Находка 4 — реальный баг: крошки/`<h1>` донора утекали в поля, сгенерированный Blade был без каркаса

Обнаружено пользователем на реальном импорте: разметка хлебных крошек донора и его `<h1>` внутри
`<main>` доходили до ИИ как обычный контент и превращались в текстовые поля/repeater — хотя крошки
на сайте рендерятся отдельным, уже подключённым везде модулем (`Breadcrumbs::render('page', $page)`,
`routes/breadcrumbs.php`), а заголовок должен идти в `Seo::name` (то самое поле, которое ВСЕ ручные
шаблоны страниц рендерят как `<h1>{{ $seo->name }}</h1>`, см. `layouts/pages/about.blade.php`).

Копнув глубже, нашлась причина шире одной находки: `SchemaBuilder::build()` всегда отдавал голый
innerHTML бывшего `<main>` (с расставленными `@field()`), а `PageBuilder::writeTemplate()` писал его
в blade-файл БЕЗ какого-либо каркаса — ни `@extends('public.layouts.main')`, ни `page_vars`/OpenGraph,
ни крошек, ни `<h1>`. У сгенерированных импортом шаблонов в принципе не было того, что есть у каждого
шаблона, написанного руками. Раньше это не всплывало, потому что живые прогоны проверяли количество
собранных полей/страниц и админ-редактор схемы, но не открывали реальный публичный URL
импортированной страницы в браузере.

**Исправлено в двух файлах:**

- `ArchiveParser::parseHtmlFile()` — новые приватные `extractHeading()`/`removeBreadcrumbNodes()`
  вырезают первый `<h1>` (возвращается отдельным ключом `heading`) и разметку крошек (эвристика:
  `<nav aria-label*="breadcrumb">` — тот же паттерн, что и в `layouts/breadcrumbs.blade.php` этого
  проекта, плюс любой узел с классом `breadcrumb`/`breadcrumbs`; вложенные `breadcrumb-item` не
  трогаются отдельно, уходят вместе с контейнером) из контентной области ДО того, как контент вообще
  попадёт к ИИ — значит, полей под них просто не заводится, вместо пост-фактум фильтрации.
- `PageBuilder::build()` — заголовком страницы (`$pageTitle`, идёт в `Page::name`/`Seo::name`/H1)
  теперь приоритетно становится извлечённый `<h1>` донора (реальный видимый заголовок), `<title>`
  остаётся запасным вариантом (как раньше) только если на странице `<h1>` не нашлось.
- `PageBuilder::wrapContent()` (новый метод) — оборачивает тело от `SchemaBuilder` в тот же каркас,
  что и `about.blade.php`: `@extends`/`page_vars` с OpenGraph/`@section('content')` с
  `Breadcrumbs::render('page', $page)` + `<h1 class="h3 mb-4">{{ $seo->name }}</h1>` перед контентом.

**Проверено** синтетическим сквозным прогоном (без реального вызова ИИ — `ArchiveParser` →
`SchemaBuilder` → `PageBuilder::wrapContent()` на реальном содержимом с крошками+`<h1>`+параграфом):
`heading` корректно извлёк текст `<h1>`, итоговая схема полей содержит ТОЛЬКО поле от реального
параграфа (0 полей от крошек/заголовка), собранный Blade компилируется без ошибок
(`blade.compiler`→`php -l`) и содержит `Breadcrumbs::render()`/`{{ $seo->name }}` на месте.
Живой прогон с реальным ИИ-вызовом на боевом архиве — не проводился в рамках этого фикса (нет
свежего архива под рукой в этой сессии), рекомендуется сделать при следующем реальном импорте.
