# План улучшений «Шаблоны страниц» / «Шаблоны блоков» (приближение к ACF)

Дата фиксации: 2026-08-11

## Контекст

Разделы админки «Шаблоны страниц» (`PagesController`) и «Шаблоны блоков» (`BlocksController`)
частично повторяют функционал ACF, но со своей архитектурой:

- Схема полей шаблона хранится как JSON в таблице `settings`
  (`template_public.layouts.pages.{name}` / `template_public.layouts.blocks.{name}`),
  сам blade-файл шаблона — отдельно на диске (`Storage::disk('local')`). Это два независимых
  артефакта, ничем не связанных на уровне кода.
- Доступные типы полей: `text`, `textarea`, `wysiwyg`, `oembed` (файл/картинка), `select`,
  `product`, `repeater`. Ещё около 10 типов уже размечены в `field.blade.php`, но закомментированы
  (`number`, `email`, `url`, `range`, `gallery`, `checkbox`, `radio`, `true_false`, `post_object`,
  `relationship`, `taxonomy`, `accordion`, `tab`).
- У поля есть только: тип, название, `slug`, признак мультиязычности (`langs`), у `select` — список
  вариантов. Нет `required`, `default`, `instructions`, conditional logic, ширины колонки.
- Нет автобиндинга: вместо `get_field('slug')` редактор жмёт «Generate», получает Blade-сниппет
  и вручную вставляет его копипастой в HTML шаблона (`generateTemplate()` в обоих контроллерах).
- Блоки вставляются в контент через шорткод `[block id="123"]` (`app/Shortcodes/BlockShortcode.php`) —
  id блока подставляется вручную, визуального пикера и живого превью нет.
- Логика подгрузки картинок/товаров в поля (`setFieldsImages`, `setRepeaterImages`,
  `setFieldsProducts`, `setRepeaterProducts`) продублирована один-в-один между `Page` и `Block`;
  подгрузка товаров в повторителе — N+1 (`Product::find()` в цикле), в отличие от уже
  батчинг-нутых картинок.
- Схема полей хранится только в БД (`settings`) — нет Local JSON синка (как в ACF), поэтому
  конфиг полей не едет через git/деплой вместе с версткой.

## Порядок реализации

Идём последовательно 0 → 1 → 2, каждая задача мёржится независимо и не ломает предыдущий
функционал (новые типы полей добавляются в existing select, старые шаблоны не трогаются).
Стартуем с 0.1 и 0.2 — самые дешёвые и разблокируют остальное.

Реализация этапа 0 идёт в ветке `feature/acf-fields-foundation` (создана от `master`,
не трогает застейдженный рефакторинг модулей). Изменения пока не закоммичены — ждут ревью.

## Заметки по ходу реализации этапа 0

- **0.1**: помимо `Page`/`Block`, точно такая же копипаста `setFieldsProducts`/`setRepeaterProducts`
  нашлась и в `PagesController` (защищённые методы) — итого было 3 копии логики товаров вместо
  заявленных двух. Удалена, вызовы переведены на `$page->setFieldsProducts()`.
- **0.1 (задел на будущее)**: похожая тройная копипаста есть и у `fillInFields`/`mergeLangFields`/
  `mergeRepeaterFields` (заполнение схемы значениями из запроса) — не трогали в рамках 0.1, чтобы не
  раздувать задачу; кандидат на отдельный рефакторинг тем же трейт-паттерном.
- **0.3**: настройки `required` на уровне поля в схеме ещё нет (она появится в 1.4) — валидатор
  уже её учитывает (`!empty($field->required)`), но пока ни на одном поле выставить эту галочку
  нельзя через UI, поэтому проверка сейчас фактически не срабатывает ни для одного шаблона.
  Реального эффекта стоит ждать после 1.4.
- **0.4**: в админке в принципе нет действия "переименовать/удалить файл шаблона" — переименование
  возможно только вручную на файловой системе (деплой/разработка), в обход UI. Поэтому вместо
  "guard" (блокировки несуществующего действия) сделали **обнаружение уже возникшего рассинхрона**:
  в списках "Шаблоны страниц"/"Шаблоны блоков" теперь отдельной строкой с предупреждением
  показываются `template`, на которые ссылаются страницы/блоки, но для которых нет blade-файла —
  раньше это приводило к тихому падению рендера на публичной части.
- **1.1**: `number` получил собственные настройки схемы (min/max/step) — единственный из шести новых
  типов, кому это нужно; остальные (`url`, `email`, `date`, `color`, `true_false`) обошлись без
  типовых настроек. Заодно поправлен снятый чекбокс `true_false`: HTML-форма не шлёт значение для
  невыбранного чекбокса, поэтому `fillInFields()` в обеих контроллерах явно приводит его отсутствие
  к `0` — без этого поле бы тихо сохраняло старое значение. По пути также поправлен мелкий
  предсуществующий баг в `admin/blocks/templates/field.blade.php` — у опции `product` не было
  атрибута `selected`, из-за чего выбор терялся при повторном открытии поля.
  Проверка синтаксиса всех новых/изменённых `.blade.php` — через `BladeCompiler::compileString()` +
  `php -l` по скомпилированному выводу (полноценный `artisan view:cache` в этом окружении падает на
  несвязанном стороннем модуле `Modules/Compare` без `resources/views`).
- **1.2**: обнаружился уже готовый JS-компонент множественного выбора файлов
  (`public/js/scripts/larchik/media-buttons.js`, `data-type="multiple"`, `.js_gallery_picture_wrapper`,
  sortable) — используется для галереи товаров/категорий и уже подключён на экранах редактирования
  страниц/блоков (`@include('admin.media.assets')`). `gallery` переиспользует его один в один вместо
  новой реализации. Ради этого обобщил `HasCustomFields`: было заточено под одиночное значение
  (id → `{id, image}`), теперь `(array)$field->value` одинаково разворачивает и одиночный id, и уже
  готовый список id — `oembed` резолвится как раньше, `gallery` — в плоский список File-моделей по
  порядку, без не найденных записей. Проверено отдельным автономным скриптом (без БД, с фейковым
  loader'ом) — включая вложенный `gallery` внутри `repeater`.
- **1.3**: `relationship` (→ `Page`) собран строго по аналогии с уже существующим `product`. `taxonomy`
  (→ `Category`) потребовал отдельного решения: у `Category`, в отличие от `Page`/`Block`/`Product`,
  нет простого `->name` — есть только оптимизированный кэширующий accessor
  (`Category::getOptimizedName()`) поверх отдельно подгружаемых `Localization`. Чтобы не завязываться
  на эту машинерию из вьюхи/composer'а, список категорий для дропдауна собирается через прямой запрос
  к `Localization` (`localizable_type = 'Categories'`), в обход `Category`-специфичной оптимизации.
  Заодно расширил `HasCustomFields` методами `setFieldsPages`/`setFieldsCategories` (тот же паттерн,
  что `setFieldsProducts`) и добавил их в цепочку хайдрации на публичном рендере
  (`PagesController::homeHtml/showAction`, `BlockShortcode`) — иначе `relationship`/`taxonomy` отдавали
  бы в шаблон голый id вместо модели. Заодно нашёлся и починен пред-существующий баг: view-composer,
  подгружающий `$products` для поля типа `product`, был подписан только на
  `admin.pages.fields.product`, из-за чего в блоках (`admin.blocks.fields.product`) `$products` не
  долетал вообще — поле `product` в блоках было фактически нерабочим.
- **1.4**: сознательно сократил список до `required` (наибольшая отдача — активирует валидатор из
  0.3), `instructions` и `default value`. `placeholder` и ширину колонки отложил:
  - `placeholder` подключался бы отдельно в 12 файлах (6 текстовых типов × pages/blocks) ради
    небольшого UX-выигрыша поверх уже существующего лейбла с названием поля — низкая отдача на
    объём правок для этого захода.
  - Ширина колонки требует перестройки грид-контейнера (сейчас поля в `fields.blade.php` просто
    идут одно под другим без `.row`/`.col` обёртки) — рискованная правка вёрстки примерно в 15
    файлах, которую нечем проверить визуально в этой сессии (нет браузера с живым приложением).
    Both — кандидаты на отдельный проход с визуальной проверкой в браузере.
  `instructions` подключил механической вставкой (`sed`) в 22 из ~30 партиалов ввода данных — там,
  где уже был единообразный `<label>{{ $field->name }}</label>`. Ещё 8 партиалов (`select`,
  `product`, `relationship`, `taxonomy` × pages/blocks, плюс `blocks/fields/textarea.blade.php`)
  такого лейбла не имеют вовсе (пред-существующий пробел, не мой), поэтому `instructions` там
  сейчас не показывается — не стал переверстывать эти файлы попутно.
  `default` не потребовал правок во вьюхах — значение подставляется в `updateTemplateData()` (оба
  контроллера) на этапе слияния схемы с уже сохранёнными данными, когда для поля вообще нет
  сохранённого значения (новая страница/блок или только что добавленное в схему поле).

  **Живое тестирование в браузере** (реальная админка на example.lh, ветка feature/acf-fields-foundation
  на диске — правки применяются сразу): добавил тестовое поле `gallery` в схему `about`, прошёл весь
  путь редактор схемы → форма ввода данных → сохранение → БД → хайдрация на публичном рендере. Нашёл
  и исправил 4 бага, которые статическая проверка (`php -l` + компиляция Blade) не могла поймать:

  1. **Коллизия id в JS.** Обработчик "Добавить поле" (`pages-templates.js`/`blocks-templates.js`)
     переименовывал `id`/`for` через `.find('.custom-control-label')`/`.find('.custom-control-input')`
     без привязки к конкретному свитчу — работало, пока в поле был только один такой свитч
     (мультиязычность). Мой новый свитч "Обязательное поле" использует те же классы (иначе не
     стилизуется) и попадал под тот же `.find()`, из-за чего его `id` перезаписывался на `langsSwitch{key}`
     и клик по лейблу "Обязательное поле" на самом деле переключал мультиязычность. Правил через
     привязку `.find()` к обёртке `.langs-control`.
  2. **Перенос текста в свитче.** `.custom-control-label` в этой теме — маленькая фиксированная
     область под иконку/трек переключателя, не под текст (весь остальной код кладёт видимый текст
     рядом, а не внутрь неё). Текст "ОБЯЗАТЕЛЬНОЕ ПОЛЕ" переносился по буквам. Переделал по
     установленному в теме паттерну: текст — отдельный `<label>`-сосед, `.custom-control-label` пустая.
  3. **Несуществующая иконка.** `bx-category` не входит в бандл boxicons этого проекта — опция
     "Категория" рендерилась без иконки. Заменил на реально существующую `bx-collection`.
  4. **Ложный провал валидации из-за рассинхрона конфига.** `config('app.locales')` = `['ua','ru']`
     (`'en'` закомментирован), но `config('app.locales_names')` включает `'en' => 'English'` — это
     пред-существующий баг конфига, не мой. Из-за него `fillInFields()` падала с
     `Undefined array key "en"` при сохранении ЛЮБОЙ страницы/блока с данными полей (репитер) —
     конфиг никогда не пропускал регрессионный тест на реальном сохранении. Поставил `?? []` в
     месте падения. После фикса всплыл каскадный эффект: мой собственный валидатор `required` (0.3/1.4)
     проверял ВСЕ ключи `$fields`, включая фантомную `en`, которая структурно никогда не получает
     значение из-за того же рассинхрона — required-поле на `en` всегда бы ложно проваливало
     сохранение (год 200, `result: 'error'`, без реального сохранения). Ограничил валидацию только
     реально включёнными локалями (`config('app.locales')`).

  Рекомендация пользователю (не моя правка, т.к. это продуктовое решение): в `config/app.php` либо
  раскомментировать `'en'` в `locales`, либо убрать `'en'` из `locales_names` — сейчас они рассинхронены.
- **1.5**: реализовал только верхний уровень (одно условие `field == /!= value`, без вложенности в
  repeater и без AND/OR групп, как в полноценном ACF) — сознательно, чтобы не городить JS-логику,
  которую негде было бы проверить. Настройка — три инпута в редакторе схемы (slug поля-условия,
  оператор, значение) вместо динамического выпадающего списка полей: список пришлось бы
  синхронизировать с добавлением/удалением/переименованием полей через ту же JS-инфраструктуру,
  где уже нашёлся один баг с коллизией id (см. 1.4) — свободный ввод slug'а безопаснее. Общий
  обработчик — в `admin.js` (единственный файл, подключённый и на редактировании страниц, и блоков),
  ищет текущее значение поля-условия по `[data-name="slug"]` и показывает/скрывает через `.toggle()`.

  Живое тестирование этого пункта наткнулось на баг самого **процесса тестирования**, не кода:
  правки в `public/js/admin/admin.js` не подхватывались обычной навигацией браузера — статический
  JS кэшируется агрессивно, а `location.reload(true)` в современном Chrome эту логику уже
  игнорирует. Раз обнаружив это, проверил логику напрямую (`fetch` + `eval` свежего файла в
  контексте страницы) — сработало корректно и на начальной загрузке (скрывает поле, если условие не
  выполнено), и на живое изменение чекбокса (показывает/скрывает мгновенно). Это ограничение именно
  этой сессии тестирования: в реальной работе после правки статических файлов браузер получит их
  при следующей обычной загрузке страницы (кэш общий, но не бесконечный), и это не имеет отношения к
  корректности самого кода.
- **1.6**: сознательно ограничил scope до записи JSON при каждом сохранении схемы (`{name}.fields.json`
  рядом с `{name}.blade.php`, оба контроллера) + fallback на чтение этого файла в самом редакторе
  схемы (`adminTemplateAction`), когда в `settings` пусто. Проверил вживую: удалил запись из
  `settings` в БД напрямую — редактор схемы `about` по-прежнему корректно показал все 7 полей из
  JSON; восстановил запись обратно. Файлы `.fields.json` не в `.gitignore` — попадут в репозиторий
  при коммите как обычные файлы.

  **Не сделано осознанно**: fallback НЕ подключен в сами точки рендера контента —
  `adminEditAction`/`adminUpdateAction` (форма редактирования страницы/блока) и
  `PagesController::homeHtml/showAction`/`BlockShortcode` (публичный рендер) всё ещё читают схему
  только из `settings`, без обращения к JSON. Значит, сейчас Local JSON спасает только *редактор
  схемы* при пустой БД, но не спасает реальные страницы/блоки от падения при рендере, если
  `settings` пуст на свежем окружении — это отдельный, более широкий проход (нужно поменять ~8 мест
  вызова `get_setting('template_...')` в обоих контроллерах и в `BlockShortcode`), который стоит
  сделать отдельным заходом с таким же живым тестированием на каждый затронутый маршрут.
