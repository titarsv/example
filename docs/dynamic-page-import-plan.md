# План: ускорение посадки динамических страниц (каталог/товар/поиск/блог/статья/чекаут/спасибо/404)

Дата фиксации: 2026-08-13 (архитектура пересмотрена в тот же день — см. правку ниже)

## Контекст и отличие от [[project-page-import-feature]]

`Modules/PageImport` (см. `docs/page-import-plan.md`) решает задачу «вытащить контент из статичной
вёрстки донора в поля ACF-шаблона» — годится для действительно статичных информационных страниц
(`about`/`faq`/`contacts`/…), где весь контент — авторский текст без бэкенд-логики.

Каталог/товар/поиск/блог/статья/чекаут/страница благодарности/404 — принципиально другая задача.
Контента для извлечения там нет: это уже рабочая динамическая логика в фиксированных файлах темы
(`resources/themes/{theme}/views/public/catalog.blade.php` и т.п.), рендерящая реальные `Product`/
`Category`/`Blog`/`Order` из БД. Донор просто рисует **другой дизайн той же самой логики**.
Значит, задача верстальщика тут — не «завести поля», а **пересадить разметку/CSS-классы донора
вокруг уже существующих `@foreach`/`{{ }}`-выражений**, не сломав саму логику. Это структурный
transplant, а не извлечение контента.

## Решение по архитектуре (зафиксировано с пользователем): отдельная точка входа, оркестратор → новая тема

Не расширяем существующий раздел «Импорт страниц» — это **отдельный** пункт админки со своим
потоком:

1. Загружается тот же ZIP-архив (донор сдаёт статичные и динамические страницы вместе, одной
   сборкой).
2. **Оркестратор** идёт по каждому найденному html-файлу и **классифицирует тип страницы**
   (`static` / `catalog` / `product` / `search` / `blog` / `article` / `checkout` / `thanks` —
   таксономия ниже).
3. Оркестратор создаёт **новую тему** тем же механизмом, что уже есть в проекте —
   `php artisan theme:make {name} --from=base` (см. `docs/themes.md`) — полная копия `base`.
4. Для каждой классифицированной страницы генерируется файл **внутри этой новой темы**
   (`resources/themes/{new-theme}/views/public/...`), заменяя ровно то, что отличается от
   `base`. Всё остальное наследуется от `base` за счёт уже готового view-fallback механизма
   (`config/view.php`) — ничего специально доделывать для этого не нужно, это ровно то, для чего
   и была построена система тем.

**Почему это принципиально безопаснее** первой версии плана (там результат транспланта нужно было
класть как ревизию поверх ЖИВОЙ активной темы, с ручным гейтом через `RecordsTemplateRevisions`):
новая тема **не активна**, пока кто-то явно не выставит `ACTIVE_THEME` — сайт всё время сборки и
ревью продолжает работать на текущей теме без единого изменения. Реальный прод-чекаут, реальный
каталог — не тронуты структурно, а не потому что мы аккуратно поставили gate. Пункт про
review-gate из первой версии плана снимается — эта архитектура закрывает ту же потребность
надёжнее.

Статические страницы архива (about-подобные) идут туда же, тем же путём, что и сейчас
(`PageBuilder`/`SchemaBuilder`), с одним изменением — целевая тема параметризуется, а не жёстко
берётся из `theme_relative_path()` (которая сейчас всегда бьёт в активную тему).

## Источник архива: не `dist/`, а исходники верстальщика (`app/`)

Раз мы всё равно создаём новую тему — имеет смысл принимать не скомпилированный `dist/`, а полный
проект верстальщика (`app/` + `package.json`/`webpack.config.js`, без `node_modules`), чтобы сразу
разложить шрифты/картинки/scss/js по местам, а не только html. Изучил оба реальных донора
(`C:\Development\Layouts\vza`, `C:\Development\Layouts\proper-loud`) — оба собраны на одном и том же
boilerplate (`package.json`: `"triplefork-project-builder"`), той же линии, что и собственный
`package.json` этого проекта (`"project-builder"`). Структура source предсказуема и одинакова у
обоих:

```
app/
  app.js                          — единая точка входа JS донора (шапка/меню/общие виджеты — нам не нужна)
  assets/
    templates/layouts/{name}.html — по файлу на страницу, имя = слаг (strains.html, catalog.html…)
    templates/parts/{header,footer}.html — общий чехол донора, не нужен (своя тема даёт header/footer)
    stylesheets/
      app.scss                    — единая точка входа SCSS донора
      _variables.scss, _mixin.scss, _vendor.scss, … — общее для всех страниц донора
      _{name}.scss                — SCSS **конкретно под каждую страницу**, то же имя, что и .html
    images/*, fonts/*             — плоские папки, чистые оригинальные имена файлов
```

Практические следствия (проверено на реальных файлах, не гипотеза):

- `app/assets/templates/layouts/{name}.html` — прямая замена `dist/{name}/index.html`, `<main>`
  внутри — обычный HTML. `<include src="...header/footer.html">` (build-time директива
  `posthtml-include`) встречается ТОЛЬКО снаружи `<main>` у обоих доноров — `ArchiveParser` работает
  без изменений, `DOMDocument` просто игнорирует незнакомый тег.
- Картинки в source ссылаются чистыми относительными путями с оригинальными (не захэшированными
  webpack'ом) именами — та же `resolveAssetPath()`, что уже есть, результат только чище.
- SCSS уже разложен по страницам 1:1 по имени — `_strains.scss` ↔ `strains.html`. Механическое
  сопоставление по имени, ИИ не нужен.

**Реальная коллизия, а не гипотетическая**: donor's `_variables.scss` определяет `$black`/`$dark`/…,
тема проекта — свои `$primary`/`$dark`/… в `resources/themes/base/scss/_variables.scss`. Оба
используют `$dark`. SCSS `@import` — не модульная система, переменные глобальны, «последняя запись
побеждает». Слить donor'ские `_variables.scss`/`_mixin.scss` в общий `app.scss` темы — значит тихо
перезаписать `$dark` для всех страниц темы после точки импорта.

**Решение — не мержить в общий `app.scss`, отдельный Mix-entry на страницу**:

- Donor-файлы для сгенерированной страницы (`_{name}.scss` + нужные ей `_variables.scss`/
  `_mixin.scss`, например ради `@include bp(...)`) копируются в `resources/themes/{new-theme}/scss/
  imported/{name}/` — отдельная подпапка на страницу, чтобы donor-переменные РАЗНЫХ импортов тоже не
  сталкивались друг с другом.
- Компилируется отдельным Mix-entry в `public/themes/{theme}/css/imported/{name}.css`, подключается
  `<link>`'ом только в сгенерированном шаблоне ЭТОЙ страницы — не участвует в общем `app.css`. Ноль
  риска коллизии переменных — физически разные CSS-файлы. `webpack.mix.js` дополняется: перебор
  `${themeSrc}/scss/imported/*` → по `.sass()`-вызову на каждую найденную подпапку (тот же паттерн,
  что уже есть у `if (fs.existsSync(...))`-проверок для images/fonts).
- Картинки/шрифты — копируются без проблем, `mix.copyDirectory()` уже рекурсивный. Кладём в
  `images/imported/`, `fonts/imported/` (подпапка — чтобы не перезаписать `favicon.png`/логотип темы
  одноимённым файлом донора).
- **JS — решение пересмотрено** (изначально в этом плане было «не автоматизируем»): найден точный,
  уже работающий прецедент — сравнил `app/app.js` донора (идентичный у vza/proper-loud) с
  `C:\OSPanel\home\nnn-site.lh\public\resources\js\app.js`, где ровно эта задача уже решена на
  реальном проекте той же линии. Схема:

  | Донорский `app.js` | `nnn-site.lh` версия |
  |---|---|
  | `require('jquery'); require('bootstrap-sass');` | `require('./bootstrap')` — свой jQuery + настоящий Bootstrap 5, не `bootstrap-sass` донора |
  | `require('./modules/forms')` и т.п. | та же папка, просто скопирована на новое место, путь не меняется |
  | `require('../node_modules/sumoselect/...')` | `require('../../node_modules/sumoselect/...')` — глубина `../` пересчитана под новое расположение файла |
  | `import './assets/stylesheets/app.scss';` | убрано — SCSS не через JS-импорт (см. отдельный Mix-entry выше) |
  | — | в конце файла: `require('./custom.js')`, который сам в конце делает `require('./larchik/filter'); require('./larchik/cart'); require('./larchik/checkout');` |

  Вся UI-логика донора (слайдеры/попапы/аккордеон/шапка) остаётся в `app.js` как есть, только с
  актуализированными путями; бизнес-логика (корзина/фильтры/чекаут) — отдельными файлами,
  дописанными `require`'ом в конец. Конфликта с UI-логикой донора нет: её обработчики навешаны на
  donor-классы, которых в унаследованных от `base` header/footer нет — просто не сработают, а не
  сломают что-то. JS-модули (в отличие от SCSS-переменных) не делят область видимости через
  `require()`, поэтому объединение в один `js/app.js` на тему безопасно — отдельный Mix-entry на
  страницу, как для CSS, тут не нужен.

  **Предпосылка (разовый рефакторинг, как и с 404 ниже)**: в текущем `resources/themes/base/js/
  app.js` этого проекта корзина/избранное/сравнение/фильтры каталога/чекаут ещё не вынесены
  отдельно — всё в одном файле (776 строк). Проверено: весь этот код навешан через
  `$(document).on(...)` на классы/id, самодостаточен, ни от чего другого в файле не зависит —
  вынос в `resources/themes/base/js/shop/{cart,wishlist,compare,filters,checkout}.js` + один
  `require('./shop')` в конце `app.js` — чистое перемещение кода без риска. После этого рефакторинга
  оркестратор для `app.js` новой темы: donor's `app/app.js` как база → вендорная шапка меняется на
  уже готовый блок инициализации jQuery/Bootstrap из текущего `app.js` темы → `app/modules/` →
  `js/modules/` (пути не меняются) → глубина `../` до `node_modules` пересчитывается (с `app/app.js`
  был 1 уровень, из `resources/themes/{theme}/js/app.js` будет 4 — как уже сейчас у `app.scss`) →
  `import '...app.scss'` убирается → в конец дописывается `require('.../shop')`.

Существующий `Modules/PageImport` (dist-based, только статика) не меняется — это отдельный,
самостоятельный оркестратор со своим форматом загрузки.

## Классификация типа страницы

Два прохода, от дешёвого к дорогому:

1. **Эвристика по пути/имени файла** — быстро, детерминированно, бесплатно. Словарь строится по
   уже реально виденным на обоих протестированных донорах именам (`page-import-plan.md`, «Проверка
   на втором доноре»): `catalog`/`shop`, `*-product`/`product`, `search-results`, `blog`,
   отдельный слаг статьи под `blog/`, `checkout`/`checkout-*` (у proper-loud их было три варианта:
   `checkout`, `checkout-cryptocurrency`, `checkout-properloudplay`), `thank-you`/`thanks`, `404`.
2. **Fallback — лёгкая ИИ-классификация** только для того, что эвристика не разобрала уверенно:
   новый узкий метод (например `classifyPageType(html, context): ?string`), возвращает ОДНО
   значение из фиксированного enum'а, а не свободный разбор — на порядок дешевле, чем
   `analyzePageMarkup()`/будущий `mapDynamicPageSlots()`.
3. **Не разобрано ни эвристикой, ни ИИ → трактуем как `static`.** Это безопасный дефолт: худший
   случай — чуть неидеальная ACF-страница, которая всё равно черновик до публикации, а не что-то,
   что может задеть динамическую логику.

**`checkout`/`thanks` классифицируются, но НИКОГДА не транспланируются.** Оркестратор узнаёт их и
осознанно НЕ генерирует для них файл — так же, как сейчас `PageBuilder::SKIP_NAMES` уже пропускает
`404`/`403`/`500`/`error` для страниц-заглушек, только здесь это не «пропустить», а «распознать и
явно отказаться трогать», с записью в лог импорта. Раз файла в новой теме нет — она наследует
РЕАЛЬНЫЙ работающий `checkout.blade.php`/`thanks.blade.php` из `base` через тот же fallback.
Ошибка классификации (перепутали checkout с чем-то другим) в худшем случае просто не сгенерирует
файл там, где могла бы — не создаёт риска сломать оплату, потому что генерация для этих типов в
принципе не предусмотрена.

## Решено: `404` заводится в тему через тонкую стабильную оболочку

Изначально казалось, что `404` не участвует в системе тем и требует спецобработки/отдельного гейта.
На деле `config/view.php` не различает `public.*` от остального — он просто
добавляет `resources/themes/{active}/views`/`resources/themes/{fallback}/views` в общий
`view.paths`, так что ЛЮБОЕ имя вида `errors.404` резолвится по тем же путям, что и `public.catalog`.
Более того, текущий `resources/views/errors/404.blade.php` УЖЕ зависит от темы —
`@extends('public.layouts.main')` тянет весь хедер/футер/меню через тот же механизм. Реально
раннего резолва «до полной загрузки приложения» (ради которого `errors/*` вынесены из тем по
`docs/themes.md`) это требует не для `404`, а для `503.blade.php` (чистый статический HTML,
без единого `@extends` — на случай, когда Laravel едва поднимается) и отчасти `403` (свой отдельный
admin-layout, не публичная тема).

**Решение**: выносим сам контент 404 в тему, оставляя `errors/404.blade.php` тонкой, навсегда
стабильной оболочкой, которую импорт больше не трогает:

```blade
{{-- resources/views/errors/404.blade.php — не меняется импортом, стабильная инфраструктура --}}
@extends('public.layouts.main')
@section('title','Error 404')
@section('content')
    @include('public.errors.404_content')
@endsection
```

`public.errors.404_content` — обычный themed-partial, живёт в `resources/themes/base/views/public/
errors/404_content.blade.php` (содержит сегодняшний хардкод) и переопределяется в
`resources/themes/{new-theme}/...` точно так же, как любой другой файл темы. Оркестратор для типа
`404` пишет туда — никакой спецобработки, никакой отдельной кнопки «применить прод немедленно»:
`404` переходит в тир полной автоматизации наравне с blog/article, полностью внутри песочницы новой
темы. Новых рисков это не добавляет — 404 и так уже зависит от `public.layouts.main`/темы, это
только формализует то, что фактически уже так работает.

## Обновлённая таблица риска

Раз ничего не уходит в прод до явного переключения темы, риск сместился с «не автопубликовать» на
«не генерировать вовсе там, где цена ошибки — сломанная бизнес-логика, а не просто кривая вёрстка»:

| Группа | Страницы | Что делает оркестратор |
|---|---|---|
| Полная автоматизация | **blog, article, 404** | Классифицирует и транспланирует в новую тему без исключений — нет денег/логики заказа, худший случай — кривая страница в неактивной теме (404 — после выноса контента в `public.errors.404_content`, см. выше) |
| Автоматизация + внимательный ревью перед активацией темы | **catalog, product, search** | Транспланирует (репитер карточки товара — через уже вынесенный общий partial `public.layouts.product`, используется и `catalog`, и `search`), но перед переключением `ACTIVE_THEME` на новую тему — обязательный визуальный просмотр (сайт можно открыть на новой теме локально/на стейджинге ещё ДО переключения основного окружения) |
| Классифицируется, но НИКОГДА не транспланируется | **checkout, thanks** (и варианты типа `checkout-cryptocurrency`) | Файл в новой теме не создаётся — наследуется рабочий `base`. Из автоматизации сюда можно унести только перенос картинок/иконок донора в медиатеку (`AssetImporter` уже умеет), без записи шаблона |

## Порядок реализации (предлагаемый)

0. ✅ **Оркестратор-каркас**: новый пункт админки (`Modules\ThemeImport`, отдельный от
   `Modules\PageImport`), приём архива **с исходниками верстальщика** (`app/`, не `dist/`),
   эвристическая классификация по имени/пути, `theme:make`-эквивалент (`ThemeForker`),
   маршрутизация `static`-страниц через существующий `PageBuilder`/`SchemaBuilder` (целевая тема
   параметризована — `PageBuilder::build()`/`writeTemplate()`/`uniqueTemplateName()` теперь
   принимают `?string $theme`), раскладка `images`/`fonts`/`scss` по местам (`AssetPlacer` —
   изолированный Mix-entry на страницу) + `webpack.mix.js` дополнен динамическим перебором
   `scss/imported/*`, сборка `js/app.js` новой темы из donor's `app/app.js` (`JsAppAssembler`).
   **Живой прогон на реальном доноре** (`proper-loud`, полный `app/`, через настоящий HTTP-путь
   контроллера → очередь): 24 страницы классифицированы верно, тема создана, 12 static-страниц
   собраны, 0 ошибок, коллизии имён с существующими шаблонами (`about`→`about-import-2` и т.д.)
   разрешены корректно, SCSS разложен, `js/app.js` собран без утечек `.scss`-импорта. Все тестовые
   данные (тема, 12 страниц, 62 медиафайла, запись импорта) удалены после проверки.
   **Побочная находка (окружение, не код)**: при быстрых правках job-класса воркер иногда падал с
   `Job is incomplete class` — `opcache.revalidate_freq=2` кэширует байткод на 2 секунды, воркер
   иногда видел устаревшую версию файла. Не баг кода — просто держать в уме при быстрой итерации
   джоб в этом окружении (`php -d opcache.enable_cli=0 artisan queue:work` как обход на время
   разработки).
0.1. ✅ **Подготовительный рефакторинг `resources/themes/base/js/app.js`**: корзина/избранное/
